# ECDS request lifecycle

The ECDS archive client preserves a queued or running request when a polling budget expires. Retrying with the same state file resumes that request, including state files marked `abandoned` by older clients. If local state is missing, submission searches the account’s outstanding S2S jobs, following pagination, and adopts an exact matching request. The account queue is shared by its producers: an identical request from another producer is the same work and may be adopted and cancelled once overage. Server creation timestamps without a timezone are treated as UTC, including in persisted state.

When another S2S selection is outstanding, submission waits and rechecks at `poll_seconds`, for at most `maximum_polls` checks or the time they span. A younger job is left alone; if it completes, submission proceeds. An outstanding S2S job at least `maximum_request_age_seconds` old is cancelled to unblock the account, even when its selection differs. Cancellation must be confirmed before submission. If younger jobs still block the account when the wait expires, retrieval raises `TimeoutError` and may be retried. An unreadable queue prevents submission. Jobs for other processes are neither adopted nor cancelled.

Archive retrievals default to one concurrent request. The queue check and submission are serialized within one Python process; the lock is released while waiting between queue checks. **This is not a distributed account lock:** two processes or hosts can both observe an empty queue and submit. Coordinate operational archivers and historical backfills sharing an account; allow only one producer to submit at a time, with operational work taking priority.

After polling its selected request times out, the client cancels that request if it has reached `maximum_request_age_seconds`. The client confirms a terminal failure status or that the job no longer exists before submitting a replacement. Failed or unconfirmed cancellation stops retrieval. At most one age-expired replacement of the selected request is submitted per retrieval call; if the replacement also exceeds the limit, it is cancelled and retrieval stops. The age includes queue time and survives restarts because it comes from the original submission timestamp. The default age limit is 24 hours; the archive CLI exposes `--maximum-request-age-seconds` to adjust it. Age is checked during account queue inspection and after a selected request’s bounded polling attempt, not by a background timer.

A process or pod exiting does not cancel its server request. Preserve the work directory when possible and restart the same selection to resume it. Expired results and server-terminal failures can still be replaced, subject to the account queue check and the existing resubmission budget.

The request age limit does not extend a pod deadline, and sequential retrieval can take longer than a parallel archive. Check completion time and account contention before changing either bound. Existing running clients keep their current behavior until restarted with the updated code.
