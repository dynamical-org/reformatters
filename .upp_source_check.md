## Question 1: DUVB/CDUVB wavelength band

### Answer

**Found: DUVB and CDUVB are the surface downward flux for RRTMG-SW band
27, 29,000-38,000 cm^-1, which is 263.16-344.83 nm. They are not a
280-315 nm integral.** Confidence: high.

UPP does not compute this spectral diagnostic. It reads the two forecast-model
fields and passes them to GRIB output. In UPP `develop` commit
[`fe4f02b41fd789e414fb4bf23ad27c58ef058ee4`](https://github.com/NOAA-EMC/UPP/tree/fe4f02b41fd789e414fb4bf23ad27c58ef058ee4),
[`sorc/ncep_post.fd/INITPOST_NETCDF.f`, lines 2827-2836](https://github.com/NOAA-EMC/UPP/blob/fe4f02b41fd789e414fb4bf23ad27c58ef058ee4/sorc/ncep_post.fd/INITPOST_NETCDF.f#L2827-L2836)
shows that relay:

```fortran
2828      VarName='duvb_ave'
2830      spval,VarName,auvbin)
2834      VarName='cduvb_ave'
2836      spval,VarName,auvbinc)
```

The exact GFS v16 forecast source maps those names to radiation diagnostic
slots 21 and 22. See
[`gfsphysics/GFS_layer/GFS_diagnostics.F90`, lines 243-268](https://github.com/NOAA-EMC/fv3atm/blob/9a9a701333305131fa7fd20ed32b8c3cf8570399/gfsphysics/GFS_layer/GFS_diagnostics.F90#L243-L268):

```fortran
245    ExtDiag(idx)%name = 'duvb_ave'
254      ExtDiag(idx)%data(nb)%var2 => IntDiag(nb)%fluxr(:,21)
259    ExtDiag(idx)%name = 'cduvb_ave'
268      ExtDiag(idx)%data(nb)%var2 => IntDiag(nb)%fluxr(:,22)
```

The radiation driver fills those slots from the all-sky and clear-sky UV-B
components. See
[`gfsphysics/GFS_layer/GFS_radiation_driver.F90`, lines 2073-2076](https://github.com/NOAA-EMC/fv3atm/blob/9a9a701333305131fa7fd20ed32b8c3cf8570399/gfsphysics/GFS_layer/GFS_radiation_driver.F90#L2073-L2076):

```fortran
2075 Diag%fluxr(i,21) = ... + scmpsw(i)%uvbfc * tem0d
2076 Diag%fluxr(i,22) = ... + scmpsw(i)%uvbf0 * tem0d
```

The RRTMG computation defines UV-B as band 27 in
[`physics/radsw_main.f`, lines 345-346](https://github.com/NCAR/ccpp-physics/blob/01ed01fb0b3112e96eb619e0339d88fb0201982f/physics/radsw_main.f#L345-L346):

```fortran
345 ! uv-b band index
346 integer, parameter :: nuvb = 27
```

It then selects that one band for both clear-sky and total-sky surface
downward fluxes in
[`physics/radsw_main.f`, lines 3037-3039 and 3059-3076](https://github.com/NCAR/ccpp-physics/blob/01ed01fb0b3112e96eb619e0339d88fb0201982f/physics/radsw_main.f#L3037-L3076):

```fortran
3038 ibd = nuvb - nblow + 1
3039 suvbf0 = fxdn0(1,ibd)
3060 suvbfc = suvbf0
...
3076 suvbfc = fxdnc(1,ibd)
```

Finally, the band table establishes the bounds. `NBLOW=16`, so band 27 is
array element `27 - 16 + 1 = 12`; see
[`physics/radsw_param.f`, lines 117-121 and 174-180](https://github.com/NCAR/ccpp-physics/blob/01ed01fb0b3112e96eb619e0339d88fb0201982f/physics/radsw_param.f#L117-L180):

```fortran
119 integer, parameter :: NBLOW = 16
175 ... wvnum1 = ... 22650.0,29000.0,38000.0, 820.0 /
178 ... wvnum2 = ... 29000.0,38000.0,50000.0, 2600.0 /
```

Thus element 12 is `wvnum1=29000 cm^-1`, `wvnum2=38000 cm^-1`.
For wavenumber `nu` in cm^-1, wavelength in nm is
`lambda_nm = 10^7 / nu`. Because wavelength reverses the endpoints:

- `10^7 / 38000 = 263.1579 nm`
- `10^7 / 29000 = 344.8276 nm`

So the band is **263.16-344.83 nm** (usually described approximately as
263-345 nm).

The modern UFS-community copy independently retains the same explicit choice:
[`RRTMG/radsw_main.F90` lines 379-380](https://github.com/ufs-community/ccpp-physics/blob/3e6660c6df54e95a0871e990c2294dd397ae3860/physics/Radiation/RRTMG/radsw_main.F90#L379-L380)
sets `nuvb=27`, and
[`RRTMG/radsw_param.f` lines 182-188](https://github.com/ufs-community/ccpp-physics/blob/3e6660c6df54e95a0871e990c2294dd397ae3860/physics/Radiation/RRTMG/radsw_param.f#L182-L188)
retains the 29,000-38,000 cm^-1 bounds.

## Question 2: HLCY storm-motion convention

### Answer

**Found: the UPP version pinned by the GFS v16.3.34 workflow (`upp_v8.3.0`)
uses the Bunkers dynamic method with a fixed 7.5 m/s right-moving deviation
globally. It has no hemisphere branch and does not read latitude. Current UPP
`develop`, however, is different: it selects the opposite/left-moving
deviation south of the equator.** Confidence: high.

The GFS v16 UPP caller sets the two helicity depths to 3000 m and 1000 m,
calls `CALHEL`, and emits `HELI(:,:,1)` for the first requested HLCY level. See
[`sorc/ncep_post.fd/MISCLN.f`, lines 168-184 at the `upp_v8.3.0` commit](https://github.com/NOAA-EMC/UPP/blob/c5f3053c9b22ac18287f14f9e255b45994cab6a3/sorc/ncep_post.fd/MISCLN.f#L168-L184):

```fortran
177 DEPTH(1) = 3000.0
178 DEPTH(2) = 1000.0
179 CALL CALHEL(...)
184 GRID1(I,J) = HELI(I,J,1)
```

The same tag's `CALHEL` header names the dynamic Bunkers method in
[`sorc/ncep_post.fd/CALHEL.f`, lines 13-21](https://github.com/NOAA-EMC/UPP/blob/c5f3053c9b22ac18287f14f9e255b45994cab6a3/sorc/ncep_post.fd/CALHEL.f#L13-L21).
The implementation uses the 0-6 km mean wind, a shear vector from the mean
0-0.5 km wind to the mean 5.5-6 km wind, and a 7.5 m/s perpendicular
right-moving deviation. The defining section is
[`CALHEL.f`, lines 329-345](https://github.com/NOAA-EMC/UPP/blob/c5f3053c9b22ac18287f14f9e255b45994cab6a3/sorc/ncep_post.fd/CALHEL.f#L329-L345):

```fortran
330 ! IT IS DEFINED AS 7.5 M/S TO THE RIGHT OF THE 0-6 KM MEAN
336 ! THIS IS FOR THE RIGHT-MOVING CASE; WE IGNORE THE LEFT MOVER.
339 USHR6(I,J) = UMEAN5 - UMEAN1
340 VSHR6(I,J) = VMEAN5 - VMEAN1
344 UST(I,J) = UMEAN6 + (7.5*VSHR6(I,J)/SQRT(DENOM))
345 VST(I,J) = VMEAN6 - (7.5*USHR6(I,J)/SQRT(DENOM))
```

There is no latitude test around that calculation. The routine's imports also
show that latitude is not available to it:
[`CALHEL.f`, lines 79-86](https://github.com/NOAA-EMC/UPP/blob/c5f3053c9b22ac18287f14f9e255b45994cab6a3/sorc/ncep_post.fd/CALHEL.f#L79-L86):

```fortran
79 use vrbls3d, only: zmid, uh, vh, u, v, zint
80 use vrbls2d, only: fis, u10, v10
81 use masks, only: lmv
```

### Current-UPP version boundary

UPP commit
[`12ab90c72627d11644734af919f900edc2083932`](https://github.com/NOAA-EMC/UPP/commit/12ab90c72627d11644734af919f900edc2083932)
("Account for left-mover in SH in SRH", 2022-10-10) added the hemisphere
switch. It is present in current `develop`. Current
[`CALHEL.f`, lines 314-322](https://github.com/NOAA-EMC/UPP/blob/fe4f02b41fd789e414fb4bf23ad27c58ef058ee4/sorc/ncep_post.fd/CALHEL.f#L314-L322)
is explicit:

```fortran
316 IF (GDLAT(I,J) >= 0) THEN
317   UST(I,J) = UMEAN6 + (7.5*VSHR6(I,J)/SQRT(DENOM))
318   VST(I,J) = VMEAN6 - (7.5*USHR6(I,J)/SQRT(DENOM))
319 ELSE IF (GDLAT(I,J) < 0) THEN
320   UST(I,J) = UMEAN6 - (7.5*VSHR6(I,J)/SQRT(DENOM))
321   VST(I,J) = VMEAN6 + (7.5*USHR6(I,J)/SQRT(DENOM))
```

Therefore:

- **Operational GFS v16 source line:** unconditional global right mover.
- **Current UPP `develop` source line:** right mover in the Northern
  Hemisphere, mirrored/left mover in the Southern Hemisphere.

The old prose comment saying "ignore the left mover" remains in current
`develop`, but it is stale: the executable branch above and the 2022 change-log
entry at [`CALHEL.f` line 31](https://github.com/NOAA-EMC/UPP/blob/fe4f02b41fd789e414fb4bf23ad27c58ef058ee4/sorc/ncep_post.fd/CALHEL.f#L31)
show the actual current behavior.
